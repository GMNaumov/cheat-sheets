# Инструкции для агентов

Правила работы со всем репозиторием `cheat-sheets`: личным хранилищем инструкций, команд, примеров конфигурации и рабочих заметок. При изменениях сохраняйте практическую пользу материалов, понятную навигацию и согласованность документации с примерами.

## Источники сведений о проекте

- Начинайте с [корневого README.md](README.md): он описывает назначение проекта, актуальные разделы и способы проверки.
- Размещение и именование файлов определяются [правилами репозитория](conventions/repository.md).
- Оформление материалов определяется [шаблоном Markdown](conventions/markdown-template.md). Выбирайте образец по назначению файла: навигация, команды, руководство или справочная заметка.
- Для идентификаторов внешних проектов и инфраструктурных ресурсов используйте [соглашения об инфраструктуре](conventions/project-infrastructure.md). Описанная там структура внешних проектов не является структурой этого репозитория.
- Перед изменением раздела прочитайте его `README.md` и связанные материалы. Если появятся вложенные `AGENTS.md`, учитывайте их правила в соответствующих каталогах.
- Сверяйте команды проверок с [README.md](README.md), [workflow GitHub Actions](.github/workflows/validate.yml) и файлами в `scripts/`. При изменении проверок поддерживайте эти источники согласованными.

## Организация и развитие репозитория

- Текущие тематические разделы перечислены в корневом `README.md`. Их список может расширяться; выбирайте место для нового материала по его содержанию.
- Дополняйте подходящий существующий раздел. Создавайте новый, если тема самостоятельная и не укладывается в текущую структуру.
- В каждой крупной тематической папке поддерживайте навигационный `README.md` с кратким описанием и ссылками на материалы.
- Руководства размещайте в `guides/`, команды — в `commands.md` или `commands/`, запускаемые конфигурации и код — в `examples/`, вложения — в `assets/` рядом с материалом.
- Для новых файлов и каталогов используйте lowercase kebab-case. Сохраняйте стандартные имена инструментов: `README.md`, `AGENTS.md`, `Dockerfile`, `compose.yaml`, `.dockerignore`, `requirements.txt`.
- Называйте руководства по задаче или результату, а справочники отдельных команд — по имени команды.
- При добавлении материала обновляйте навигацию соответствующего раздела; при добавлении раздела верхнего уровня — также корневой `README.md`.
- При перемещении или переименовании файлов обновляйте входящие ссылки и зависимые пути в конфигурациях и инструкциях.
- Развивайте структуру по мере появления содержимого. Не создавайте пустые разделы и каталоги для предполагаемых будущих тем.

## Язык и оформление материалов

- Пишите пояснения и заголовки на русском языке. Сохраняйте оригинальные имена технологий, команд, параметров и полей конфигурации.
- Сохраняйте текстовые файлы в UTF-8; при чтении и записи проверяйте корректность кириллицы.
- Начинайте Markdown-файл с одного заголовка `#` и краткого описания назначения. Соблюдайте последовательность уровней `##`, `###`.
- Следуйте подходящему образцу из `conventions/markdown-template.md`; для коротких заметок используйте только необходимые разделы.
- Если меняете стиль материала, применяйте это изменение ко всем аналогичным файлам репозитория. Исправление отдельной фактической ошибки не требует переформатирования других материалов.
- Перед командой объясняйте её назначение, условия выполнения и нужное окружение. В руководствах указывайте необходимые зависимости и способ проверки результата.
- Предупреждения о необратимых последствиях размещайте непосредственно перед соответствующей командой. Необратимые действия в руководствах выделяйте в отдельный шаг.
- Используйте ограждённые блоки кода с указанным языком: `bash`, `powershell`, `yaml`, `python`, `text` и другие по содержимому.
- В блоках команд оставляйте текст для копирования, а заменяемые значения обозначайте понятными заполнителями. Поясняйте неочевидные флаги и ограничения без повторения очевидного.
- Используйте относительные ссылки с содержательными подписями. Сохраняйте регистр имён файлов в путях, чтобы ссылки работали и в Linux.
- Не добавляйте горизонтальные разделители, пустые разделы и необязательные метаданные.
- Соблюдайте [конфигурацию markdownlint](.markdownlint-cli2.jsonc). Не ослабляйте проверки ради обхода ошибок оформления.

## Примеры и конфигурации

- Поддерживайте соответствие команд в документации реальным файлам примера: именам сервисов, путям, портам, переменным окружения и зависимостям.
- Для Compose-примеров предпочитайте команды с именем сервиса (`docker compose exec ollama`), чтобы инструкции не зависели от `container_name`. Перед обращением к API после запуска используйте проверку готовности сервиса.
- Для запускаемого примера документируйте необходимые условия, порядок запуска и проверку результата в его `README.md`.
- В локальных Compose-примерах привязывайте опубликованные порты к `127.0.0.1`, если доступ из сети не является явной частью задачи. Отключённую авторизацию описывайте вместе с границами такого режима.
- Явно обозначайте неполные демонстрационные фрагменты и отличайте их от конфигураций, пригодных для запуска.
- Указывайте платформу и версии, если от них зависит поведение команды или совместимость примера. При изменении таких условий обновляйте связанные пояснения.
- При смене контейнерного образа проверяйте его пользователя, каталоги данных и совместимость форматов. Сохранение имени тома не подтверждает совместимость; документируйте резервное копирование и переход с прежней конфигурации.
- Проверяйте относительные пути Compose, включая контексты сборки, Dockerfile, bind mounts и env-файлы; локальные зависимости запускаемых примеров должны находиться в репозитории.
- Используйте заполнители для секретов и персональных значений. Не добавляйте реальные учётные данные, локальные окружения и сгенерированные файлы Python.
- Команды установки, удаления, запуска сервисов и загрузки моделей из материалов являются примерами для читателя. Выполняйте их только когда это требуется задачей, учитывая изменения в окружении и расход ресурсов.
- Проверяйте изменяемые сведения о сторонних инструментах по официальной документации; указывайте источник и существенные ограничения версий рядом с материалом.

## Проверки изменений

Выполняйте команды из корня репозитория. Для изменений Markdown запускайте проверку локальных ссылок и линтер; остальные проверки выбирайте по затронутым файлам.

Проверка локальных ссылок и якорей в Markdown:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-markdown-links.ps1
```

Проверка Markdown требует Node.js и `npx`:

```powershell
npx --yes markdownlint-cli2@0.24.0 "**/*.md" "#node_modules"
```

При изменении Compose-файлов или связанных локальных путей проверяйте пути скриптом. Требуется Docker CLI с Compose:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-compose-paths.ps1
```

Для каждого изменённого Compose-файла дополнительно проверяйте конфигурацию, подставляя его путь:

```powershell
docker compose -f <путь-к-compose.yaml> config --quiet
```

При изменении валидаторов запускайте регрессионные проверки. Они требуют Docker CLI с Compose, но не запускают контейнеры и не загружают образы:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-validators.ps1
```

Валидатор должен завершаться с ненулевым кодом при ошибке чтения, разбора или внешней команды. Отделяйте диагностический вывод от JSON и проверяйте пути сервисов во всех профилях Compose, включая `env_file` и стандартный `Dockerfile`.

При изменении Python-примеров проверяйте синтаксис. Для текущих примеров Ollama используйте Python 3:

```powershell
python -m compileall -q .\llm\ollama\examples
```

В Linux и macOS используйте `python3`, если интерпретатор установлен под этим именем. Для PowerShell-скриптов используйте доступный `pwsh`, если `powershell` отсутствует. При появлении Python-примеров в других разделах включайте их в соответствующие локальные и CI-проверки.

GitHub Actions выполняет проверки при push и pull request. Проверка ссылок, линтер, компиляция Python и `docker compose config` проверяют отдельные свойства файлов; они не подтверждают успешный запуск примеров. Если задача требует проверки запуска, выполняйте её отдельно в подходящем окружении.

## Порядок завершения работы

- Ограничивайте изменения поставленной задачей, сохраняйте существующие правки пользователя и избегайте несвязанного переформатирования.
- Проверьте итоговый diff, навигацию и соответствие документации изменённым примерам.
- В ответе кратко укажите, что изменено, какие проверки выполнены и какие не удалось выполнить с указанием причины. Не называйте непроведённые проверки успешными.
- При изменении назначения проекта, соглашений или способов проверки обновляйте этот файл вместе с соответствующей документацией. Подробные правила храните в профильных документах, а здесь поддерживайте актуальные ссылки и инструкции для работы.
