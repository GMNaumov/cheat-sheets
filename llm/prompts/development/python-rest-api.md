# Промпт для разработки Python REST API

Шаблон запроса для добавления регистрации пользователя в существующий асинхронный API. Перед отправкой модели уточните версии зависимостей и структуру проекта в контексте.

## Роль

Ты — senior Python-разработчик. Помоги решить задачу.

## Контекст

- Python 3.11, FastAPI, Pydantic 2, SQLAlchemy 2 с `AsyncSession`, PostgreSQL.
- Небольшой REST API.
- Есть модель `User`: `id`, `email`, `password_hash`, `created_at`.

## Задача

Добавь endpoint `POST /users` для регистрации пользователя.

## Требования

- Валидировать email через `EmailStr` и использовать единое нормализованное значение при проверке и сохранении. Политика приложения: регистр всего адреса не учитывается; после валидации применять `casefold()`.
- Требовать пароль длиной не менее 12 символов.
- Проверять уникальность email и добавить соответствующее ограничение на уровне PostgreSQL.
- Обрабатывать гонку одновременных регистраций через ошибку нарушения уникальности БД, а не только предварительный `SELECT`. Возвращать `409` только для именованного ограничения уникальности email; другие ошибки БД не маскировать. После неудачной записи откатывать транзакцию.
- Добавить миграцию ограничения уникальности. Учесть нормализацию существующих адресов и возможные дубликаты: описать проверку и разрешение конфликтов без автоматического удаления пользователей.
- Хешировать пароль через `pwdlib[argon2]` с Argon2id. Выполнять вычисление хеша вне цикла событий, например через пул потоков.
- Возвращать `201` и данные пользователя через отдельную схему ответа без пароля и `password_hash`. Не записывать пароль и хеш в логи.
- При дубликате email возвращать `409`.

## Ограничения

- Не изменять существующие поля модели; при необходимости можно добавлять новые.
- Использовать Pydantic-схемы.
- Код должен быть асинхронным.

## Тесты

- Успешная регистрация пользователя.
- Отклонение некорректных email и короткого пароля.
- Отклонение повторной регистрации с тем же email.
- Отклонение повторной регистрации с email в другом регистре.
- Обработка конкурентных запросов с одинаковым email на реальной PostgreSQL с независимыми сессиями: один ответ `201`, второй `409`, в БД одна запись.
- Восстановление работоспособности сессии после конфликта; посторонняя ошибка БД не превращается в `409`.
- Пароль не хранится открытым текстом, хеш проверяется выбранной библиотекой и отсутствует в ответе.

## Формат ответа

План, код по файлам, пример запроса, тесты.
Если не хватает данных — задай вопросы.

## Основание выбора хеширования

В [руководстве FastAPI по безопасности](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/#password-hashing) для новых хешей используется `pwdlib` и рекомендуется Argon2. Для существующего проекта с другими хешами отдельно уточните требования к их проверке и миграции.
